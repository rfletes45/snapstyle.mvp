## 11. Keyboard Architecture

### Executive Summary

The keyboard architecture has gone through 3 iterations trying to solve a fundamental problem: making the chat composer track the keyboard smoothly while the inverted FlatList also resizes correctly.

### Runtime Environment

- `KeyboardProvider` already wraps the app
- `useReanimatedKeyboardAnimationCompat()` is the live keyboard-height source
- on native builds that hook uses keyboard-controller shared values when available
- on Expo Go it falls back to RN `Keyboard` events
- the KCSV scroll component code still exists in `ChatKeyboardScrollView.tsx`, but `kcsvAvailable` is intentionally hardcoded to `false`

### Expo Go Keyboard Fallback

`src/utils/optionalKeyboardController.tsx` provides `useFallbackKeyboardAnimation()`, a compatibility bridge that feeds RN `Keyboard.addListener` events into Reanimated shared values so chat screens animate correctly in Expo Go. It uses `keyboardWillShow`/`keyboardWillHide` on iOS and `keyboardDidShow`/`keyboardDidHide` on Android, then animates the shared values with `withTiming`.

### The Fundamental Problem

Both KSV and KAV are designed for "simple" keyboard avoidance. The chat screen requires a specific combination of:

1. **Inverted FlatList** - newest messages at bottom, `maintainVisibleContentPosition` active
2. **Composer at bottom** - must sit flush above the keyboard when open
3. **Message list must resize** - visible area must shrink when keyboard opens
4. **Conditional safe area** - bottom safe area needed when keyboard closed, not when open
5. **Interactive keyboard dismiss** - iOS drag-to-dismiss must be smooth

### Why KSV Fails

KSV uses `translateY`, which is a visual-only transform. It does not trigger flex layout changes. The FlatList still occupies the same pixel count. Only the footer moves, floating over the bottom messages.

### Why KAV `behavior: "height"` Fails

KAV's `"height"` behavior sets explicit `height` plus `flex: 0`. This triggers layout change, but:

- layout is async between the Reanimated UI thread and RN Yoga JS thread, which causes visible lag and jitter
- the flex transition from `flex: 1` to an explicit height is discontinuous
- the safe-area spacer can remain visible and create a gap
- stale `initialFrame` measurements create jumpy transitions

### Current Architecture (Fallback Container + Shared Keyboard Values)

All three chat screens now share one keyboard stack:

- `ChatKeyboardContainer` currently resolves to `FallbackKeyboardContainer` in every build
- the active path is an animated `paddingBottom` container driven by shared keyboard values plus composer-sheet state
- `ChatFooterWrapper` keeps the composer attached to that same bottom region
- `renderScrollComponent` resolves to a plain `ScrollView` wrapper because the KCSV scroll component is deliberately disabled
- `ComposerSheetContext` coordinates keyboard-to-sheet replacement, handoff floor, and interaction gates so picker sheets and keyboard transitions do not fight each other

Why the KCSV scroll component is off today:

- it produced visible chat-list motion during sheet-to-keyboard and keyboard-to-sheet transitions
- the simpler fallback container matched the behavior users preferred in Expo Go
- native builds still keep the good part of keyboard-controller integration: the shared keyboard-height driver used by `useReanimatedKeyboardAnimationCompat()`

**Note:** The older KAV `behavior="height"` approach described in prior doc versions has been fully replaced, and the older "native KCSV path is primary" wording is now stale.

### Requirements

Must have:

1. Messages must scroll up when keyboard opens (FlatList shrinks)
2. Composer flush above keyboard (no gap)
3. Composer above safe area when keyboard closed
4. Smooth animation (no jitter/stutter)
5. Interactive dismiss works (iOS drag-to-dismiss)
6. Works in Expo Go
7. `maintainVisibleContentPosition` must not fight keyboard
8. Works in both stacked and bubble display modes
9. Works for both `ChatScreen` and `GroupChatScreen`

### Scroll Component Status

`KeyboardChatScrollView` remains in the codebase as a dormant option, but it is not the active production path. `ThreadScreen` also stays on the fallback path even conceptually because it uses a non-inverted list and does not need the chat-scroll adapter.
